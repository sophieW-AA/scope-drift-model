# Core-Analytics

## Before you query (correctness rules)

These three rules prevent silent zero-row results and cross-space data leakage. They apply to every query in this skill regardless of tier or dataset.

### article_id vs article_id_original — know the difference

Every `reporting_data_mart` article row has two IDs:

| Column | Value range | When to use |
|--------|------------|-------------|
| `article_id` | 16-digit composite key | Only within `reporting_data_mart` (e.g. joining `article` -> `author` in the same dataset) |
| `article_id_original` | ~1–1.8M integer | **All cross-dataset joins**: Salesforce, peer_review, production_forum, AIRAK via PublicationSource, senscience |

**WARNING:** using `article_id` (internal) when crossing datasets will silently return zero rows.

### Filter by space whenever `space_id` exists

Every query on a table that carries `space_id` must include a space filter. External / bibliometric datasets (`airak`, `openalex`, `crossref`, `orcid`, `ringgold`, `dimensions`) have no `space_id` — the rule does not apply there. Salesforce uses `SpaceId__c` instead (see below).

```sql
-- DWH tables
WHERE space_id = 1   -- 1 = frontiersin.org

-- Salesforce tables
WHERE SpaceId__c = 'a3G4K0000000CmXUAU'   -- frontiersin.org SF GUID
```

**WARNING:** omitting this returns data from all publishing spaces (Frontiers Publishing Partnerships, ALF, SSPH, etc.) mixed together.

### Cross-dataset joins — read the integration map first

**WARNING:** several intuitive joins are confirmed broken (return zero rows or wrong results). Before writing any JOIN that crosses datasets, read `references/dataset-integration-map.yaml`. It contains confirmed join keys, required `SAFE_CAST` calls, and explicitly marked anti-patterns (`IGNORE [DO NOT USE]`).

### How to search the large JSON files (context guardrail)

**DO NOT** call `Read` on `references/bigquery-schemas.json` or `references/bigquery-tables.json` without `offset`/`limit` — the first is ~1.3 MB / ~60 000 lines and will blow the context window on a single call. Use `Grep` (or `rg`) with the patterns below and only fall back to a scoped `Read` once you know the line range.

**Structure of the files:**

```json
// bigquery-schemas.json
{
  "<project>.<dataset>": {
    "<table>": [
      { "col": "<name>", "type": "<BQ type>", "nullable": true|false },
      ...
    ]
  }
}

// bigquery-tables.json
{
  "<project>": {
    "<dataset>": [
      { "name": "<table>", "type": "BASE TABLE" | "VIEW" },
      ...
    ]
  }
}
```

**Recipes — always prefer `Grep` with `-n` so you get line numbers for a follow-up scoped `Read`:**

| Goal | Tool call (ripgrep equivalent: `rg -n "<pattern>" <file>`) |
|---|---|
| Find the start line of a dataset block in schemas | `Grep pattern='"<project>\.<dataset>"' path=references/bigquery-schemas.json -n=true` — e.g. `"ocean-breeze-tier-1\.reporting_data_mart"` |
| Find the start line of a specific table's columns | `Grep pattern='"<table>":\s*\[' path=references/bigquery-schemas.json -n=true` — e.g. `"article":\s*\[` |
| Confirm a column exists on any table | `Grep pattern='"col":\s*"<column>"' path=references/bigquery-schemas.json -n=true -C=2` |
| Check whether a table exists anywhere in the lakehouse | `Grep pattern='"name":\s*"<table>"' path=references/bigquery-tables.json -n=true` |
| List every table in a dataset | 1) `Grep pattern='"<dataset>":\s*\[' path=references/bigquery-tables.json -n=true` to get the start line, then 2) `Read` with `offset=<line>` and `limit=200–600` (one object per 3 lines). |

**After grep, use scoped `Read`** — once `Grep` returns a line number, call `Read` with `offset=<line>` and `limit=<~100–500>` to pull just that table's column block. Never call `Read` without both `offset` and `limit` on these two files.

**Cost example:** `"article":\s*\[` on `bigquery-schemas.json` returns ~10 hits with 1 line each = ~10 tokens. Reading the table's columns with `offset`/`limit=500` = ~500 lines. A bare `Read` of the whole file = ~300 000 tokens.

**Step 4 (cross-dataset queries only): before any JOIN across datasets, open `references/dataset-integration-map.yaml`** — see the *Cross-dataset joins* rule in *Before you query* above for why.

## Connection

```python
from google.cloud import bigquery
client = bigquery.Client(project="gcp-innovation-hub")

# IMPORTANT: Use .result() not .to_dataframe() to avoid BQ Storage API permission issues
rows = list(client.query(
    "SELECT article_id_original, article_id, doi, title FROM `ocean-breeze-tier-1.reporting_data_mart.article` "
    "WHERE space_id = 1 LIMIT 5"
).result())

# To get a DataFrame, convert manually:
import pandas as pd
df = pd.DataFrame([dict(row) for row in rows])
```

## Query Best Practices

### Always SELECT specific columns
Tier 1 tables are very wide (the `article` table has 486 columns). Never use `SELECT *`.

```sql
-- **Good** — explicit column list; space filter required by the rule above
SELECT article_id, article_id_original, doi, title, stage, is_published
FROM `ocean-breeze-tier-1.reporting_data_mart.article`
WHERE space_id = 1
  AND is_published = TRUE

-- **Bad** — scans all 486 columns
SELECT * FROM `ocean-breeze-tier-1.reporting_data_mart.article`
WHERE space_id = 1
```

### Use LIMIT during exploration
Always add `LIMIT` when exploring unfamiliar tables.

```sql
SELECT article_id_original, article_id, title, create_date
FROM `ocean-breeze-tier-1.reporting_data_mart.article`
WHERE space_id = 1
LIMIT 10
```

### Prefer Tier 1 over lower tiers
The `reporting_data_mart` tables are pre-joined and enriched. Use lower tiers only when you need raw or system-specific data not available in Tier 1.

### Cost awareness
Large tables like `airak.Author` (150M rows, 14 GB) and `airak.Publication` (163M rows, 31 GB) can be expensive to scan. The `impact_data_platform_v1.t_daily_metrics` table (3.1B rows, 212 GB) and `airak.publications` (458M rows, 168 GB) are even larger. Always filter early and select only needed columns.
